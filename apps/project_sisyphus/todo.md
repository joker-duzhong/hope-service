# 🚀 Project Sisyphus (西西弗斯认知引擎) - MVP 开发任务清单

## 📍 核心交互流说明

本项目的核心不是传统的“用户问，AI答”，而是一个**状态机驱动的动态脚手架系统**。
1. **初始化：** 用户进入，后端查库获取今日需复习的知识点（节点），交由【场景生成大模型】生成一个带冲突的生存场景发送给前端。
2. **核心循环：** 用户尝试输入 -> 后端【导师大模型】评估 -> **后端严格输出 JSON** -> 前端解析 JSON 动态渲染出 UI 组件（自由输入框 / 填空题 / 乱序重组）。
3. **死锁熔断：** 同一知识点，用户如果连续失败 3 次，系统触发熔断，直接给出正确答案结束当前循环。
4. **异步沉淀：** 对话结束后，后端【提取器大模型】在后台静默分析刚刚的对话，提取新的知识节点和错误模式，更新到用户的“认知图谱数据库”中。

---

## 🛠️ 后端开发任务 (Backend & Logic)

*设计原则：后端是系统的大脑，负责维持状态机、调度不同的大模型 Agent、执行间隔重复算法，并保证输出严格的结构化数据。*

### 模块 1：数据库抽象与基础 CRUD
- [ ] **B-1.1 设计 KnowledgeNode (知识节点) 表**
  - **描述:** 存储用户的知识突触。不要写死为单词或语法，必须是抽象的节点。
  - **字段要求:** `user_id`, `node_id` (唯一标识), `domain` (学科领域, 当前默认 'esl'), `concept_description` (节点内容，如 'refund' 或 '被动语态'), `mastery_score` (0-10掌握度), `next_review_at` (下次复习时间戳).
  - **[未来考量]:** `domain` 字段的加入是为了以后无缝接入数学、法学等跨学科内容。
  - **验收标准:** 能够成功插入、查询指定用户的知识节点。
- [ ] **B-1.2 设计 InteractionLog (交互日志) 表**
  - **描述:** 记录每一次用户输入与 AI 反馈。
  - **字段要求:** `session_id`, `turn_number`, `user_input`, `ai_json_response`, `time_taken_ms`, `is_deadlock_triggered`.
  - **验收标准:** 每次交互后完整存入，能根据 `session_id` 按顺序取回对话历史。

### 模块 2：AI 引擎层 (Agent Orchestration)
- [ ] **B-2.1 实现“场景生成器” (Scenario Generator Agent)**
  - **描述:** 接收今天的待复习 Node 列表，请求 LLM 生成一个包含这些节点的全新情境。
  - **验收标准:** 给定节点 `["refund", "被动语态"]`，LLM 能稳定输出包含中文情境描述和考核目标的 JSON。
- [ ] **B-2.2 实现核心“苏格拉底导师” (Tutor Engine Agent)**
  - **描述:** 最核心逻辑。接收用户输入、当前轮数、最近3轮历史。强制大模型不给答案，只给提示。
  - **限制条件:** 必须强制大模型输出如下 JSON 结构：`{ "thought_process": "", "emotional_support": "", "interaction_type": "chat|cloze|reorder", "ai_speech": "", "component_data": {}, "is_target_met": bool }`。
  - **[未来考量]:** 这里的 Prompt 必须独立解耦，方便后期针对不同学科（如代码 debug）无缝替换 Prompt。
  - **验收标准:** 无论用户怎么套话，只要 `fail_count < 3`，模型绝不输出完整正确答案，且每次都返回合法的 JSON。
- [ ] **B-2.3 实现“知识提取机” (Memory Extractor Agent)**
  - **描述:** 接收一段完整的 Session 历史，提取出用户犯的错和新知识，转换为 KnowledgeNode。
  - **验收标准:** 能从非结构化的对话文本中，准确识别并输出符合 `KnowledgeNode` 结构的 JSON 数组。

### 模块 3：核心业务逻辑与状态机
- [ ] **B-3.1 核心对话流管理器 (Dialogue State Manager)**
  - **描述:** 负责在每次 `/chat` 请求时，维护上下文（截断最近 3 轮），并统计当前目标的失败次数 (`fail_count`)。
  - **验收标准:** 当 `fail_count` 达到 3 时，强制覆盖大模型 Prompt，要求大模型直接输出完美答案，并将该节点的 `mastery_score` 扣分。
- [ ] **B-3.2 接入间隔重复调度算法 (SRS Scheduler)**
  - **描述:** 实现或接入纯数学的记忆调度算法（类似 FSRS 或简化的 SM-2）。
  - **验收标准:** 输入一个节点的当前掌握度和历史复习记录，能准确计算出 `next_review_at` 的具体时间戳。绝对不依赖大模型进行时间计算。

### 模块 4：API 接口暴露
- [ ] **B-4.1 创建 `/start-session` 接口**
  - **描述:** 获取当天的复习节点 -> 调度场景生成器 -> 返回首条场景设定。
- [ ] **B-4.2 创建 `/chat` 接口**
  - **描述:** 接收前端用户输入 -> 调用对话流管理器与导师 Agent -> 返回带有交互类型的 JSON 结构给前端。
- [ ] **B-4.3 创建 `/challenge` (我不服) 接口**
  - **描述:** 接收用户对 AI 判决的抗议，调用独立的裁决 Prompt，返回新的判决结果。


#### 模块 5：冷启动与目标解析引擎 (Cold Start Engine)
- [ ] **B-5.1 新增 `/set-goal` (设定学习目标) 接口**
  - **描述:** 接收用户的一句话目标（例如：“我要去日本旅游”、“我要准备考雅思”）。
  - **验收标准:** 接口能够接收字符串，并调用 `Goal Deconstructor Agent`。
- [ ] **B-5.2 实现“目标解构器” (Goal Deconstructor Agent)**
  - **描述:** 专门处理冷启动的 Prompt 引擎。接收自然语言目标，输出一个 JSON 数组，包含 3-5 个为了达成该目标必须掌握的 `KnowledgeNode`。
  - **验收标准:** 给定目标“餐厅点牛排”，必须输出类似 `{"nodes": [{"concept": "medium rare", "domain": "esl"}, {"concept": "side dish", "domain": "esl"}]}` 的 JSON，并**自动存入数据库**。
- [ ] **B-5.3 改造 `/start-session` 接口的路由逻辑 (Router Logic)**
  - **描述:** 当用户点击开始学习时：
    *   **If (数据库当日有需要复习的节点):** 走正常的 SRS (间隔重复) 逻辑，提取旧节点生成场景。
    *   **Else If (数据库里有节点，但今天没复习任务):** 随机挑几个还没完全掌握的旧节点生成场景。
    *   **Else (数据库纯空，全新用户):** 不询问，直接硬编码下发一个“基础探针场景”（如咖啡店点单），或者触发 `/set-goal` 流程。
  - **验收标准:** 彻底解决全新用户的报错或白屏问题，保证任何人点进来立刻就能开局。
